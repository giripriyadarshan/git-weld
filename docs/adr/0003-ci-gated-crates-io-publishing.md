# Delegate crates.io publishing to CI after GitHub Release packaging

`git-weld` configures `cargo-release` with `publish = false` so local release preparation only bumps `[workspace.package].version` in `Cargo.toml` and `Cargo.lock`, updates `CHANGELOG.md` through `git-cliff`, commits `Prepare v<version>`, and pushes the `v<version>` tag, while `.github/workflows/release.yml` performs the actual `cargo publish` using GitHub Actions OIDC Trusted Publishing (`rust-lang/crates-io-auth-action@v1`) after the GitHub Release and all `cargo-binstall` binary archives are uploaded. `crates/git-weld/Cargo.toml` sets `[package.metadata.binstall].pkg-url` to `{ repo }/releases/download/v{ version }/...`, so running `cargo publish` locally during `cargo release` before CI finishes building the release archives would create a window where `cargo binstall git-weld` resolves the new version on crates.io and fails with `404 Not Found` on the missing GitHub Release assets. Keeping publishing in the tag-triggered CI workflow also avoids storing long-lived crates.io API tokens on maintainer machines.
